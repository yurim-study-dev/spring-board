# 1. 필수 산출물 정의 및 작성 기준

## 1.1 프로젝트 기획서 (Project Proposal)
### 1.1.1 정의
프로젝트의 출발점으로서 개발하고자 하는 서비스의 목적, 배경, 핵심 기능, 구현 타임라인 및 팀원별 역할 분담을 명확히 규정하는 기본 기획 문서.

### 1.1.2 작성 필요성 및 목적
- 프로젝트 방향성 통일: 팀원 간 서비스 목표에 대한 이해도를 일치시키고 개발 진행 중 발생할 수 있는 기획 혼선 차단
- 개발 범위 명확화: 제한된 일정에 최적화된 현실적인 개발 목표 및 서비스 스코프 설정

### 1.1.3 필수 포함 항목
- 프로젝트명 및 한 줄 서비스 소개
- 프로젝트 기획 배경 및 목적
- 서비스 주요 특징
- 주요 기능 요구사항 요약
- 팀 구성 및 도메인별 역할 분담표

- 💻 프로젝트 기획서 샘플: [docs/01_planning/01_proposal.md](docs/01_planning/01_proposal.md)

## 1.2 요구사항 기능 명세서 (PRD - Product Requirement Document)
### 1.2.1 정의
시스템이 제공해야 하는 모든 세부 기능을 도출하고, 각 기능별 구현 조건, 담당자, 우선순위를 목록화하여 관리하는 문서.

### 1.2.2 작성 필요성 및 목적
- 개발 스코프 제어: 2주 개발 일정 동안 구현할 기능과 제외할 기능을 명확하게 구분
- 개발 구현 기준 제공: 기능별 구현 방식과 세부 동작 요구조건을 구체화하여 개발 오차 감소
- 일정 관리 기반: 각 기능에 우선순위(1순위, 2순위, 3순위)를 부여하여 지연 발생 시 빠른 의사결정 지원

### 1.2.3 필수 포함 항목 및 작성 방법
- 요구사항 식별 ID: `REQ-USER-01`, `REQ-POST-01`, `REQ-REPLY-01` 등 도메인별 고유 코드 부여
- 구분: 회원, 게시글, 댓글 등 기능 도메인 명시
- 기능명 및 담당자: 기능을 담당하여 개발할 팀원 지정
- 우선순위: 1순위(필수 구현), 2순위(주요 권장), 3순위(추가 선택) 구분
- 상세 내용: 기능의 세부 동작 조건 및 입력 데이터 검증 규칙 명시

- 💻 요구사항 기능 명세서 샘플: [docs/01_planning/02_prd.md](docs/01_planning/02_prd.md)

## 1.3 시스템 아키텍처 구성도 (System Architecture Diagram)
### 1.3.1 정의
브라우저 클라이언트부터 스프링 부트 서버 애플리케이션 계층, 데이터베이스 간의 전체적인 시스템 구조와 데이터 흐름을 시각화한 구성도.

### 1.3.2 작성 필요성 및 목적
- 3-Tier Layered Architecture 이해: Presentation Layer, Application Layer, Data Layer 계층 간 역할 분리 파악
- 기술 구성 요소의 흐름 파악: Controller, Service, Repository(JdbcTemplate), View(Thymeleaf), Interceptor 간 데이터 전달 경로 명확화

### 1.3.3 필수 포함 항목
- 클라이언트 영역: 브라우저, HTTP Request / Response 통신
- Web / Presentation 계층: Spring MVC Controller, HandlerInterceptor, Thymeleaf View Resolver
- Business / Data Access 계층: Service, Spring JDBC (JdbcTemplate & RowMapper)
- Storage 계층: MySQL 데이터베이스

- 💻 시스템 아키텍처 구성도 샘플: [docs/02_design/01_architecture.md](docs/02_design/01_architecture.md)

## 1.4 데이터베이스 ERD (Entity Relationship Diagram)
### 1.4.1 정의
시스템에서 사용하는 데이터 테이블 구조, 컬럼 데이터 타입, PK/FK 제약조건 및 테이블 간의 연관 관계(1:1, 1:N, N:M)를 규정한 개체 관계도.

### 1.4.2 작성 필요성 및 목적
- 데이터 무결성 확보: 올바른 테이블 기본키(PK)와 외래키(FK) 설정을 통한 정규화 및 무결성 유지
- SQL 쿼리 작성 효율 증대: 개발 착수 전 미리 데이터 구조를 정립하여 테이블 수정 최소화

### 1.4.3 필수 포함 항목
- 테이블명 및 컬럼 명세: PK, FK, Not Null, Unique, Default 제약조건 명시
- 관계 표기선: 1 대 N 등 테이블 간 연관관계 기호 표기
- 작성 방식: 마크다운 내부 Mermaid `erDiagram` 문법 구문을 사용하여 깃허브 상에서 시각적 다이어그램으로 렌더링되도록 작성

### 1.4.4 Mermaid ERD 주요 문법
- Mermaid ERD 공식 문법 문서: [https://docs.mermaidviewer.com/diagrams/er.html](https://docs.mermaidviewer.com/diagrams/er.html)
- Mermaid ERD 관계 표현 기호 규칙:
  - 1:1 관계 (필수 1 대 1): `||--||` (양쪽 모두 1개 필수)
  - 1:1 관계 (필수 1 대 선택 0 또는 1): `||--o|` (한쪽은 1개 필수, 반대쪽은 0개 또는 1개)
  - 1:N 관계 (필수 1 대 1 이상 N): `||--|{` (한쪽은 1개 필수, 반대쪽은 1개 이상 필수)
  - 1:N 관계 (필수 1 대 0 이상 N): `||--o{` (한쪽은 1개 필수, 반대쪽은 0개 이상 선택)
  - N:M 관계 (1 이상 N 대 1 이상 M): `}|--|{` (양쪽 모두 1개 이상 필수)
  - N:M 관계 (1 이상 N 대 0 이상 M): `}|--o{` (한쪽은 1개 이상 필수, 반대쪽은 0개 이상 선택)
- 관계선 기호 가이드:
  - `||`: 정확히 1개 (Exactly one)
  - `|{`: 1개 이상 (One or more)
  - `o{`: 0개 이상 (Zero or more)
  - `o|`: 0개 또는 1개 (Zero or one)
- 기호 구성 요소 해설:
  - Straight Line (`|`): 최소 1개 이상 존재해야 함 (Mandatory 필수 조건)
  - Circle (`o`): 0개일 수 있음 (Optional 선택 조건, 없어도 됨)
  - Crow Foot (`}` 또는 `{`): 다수 (Many, N개)를 의미
- N:M 관계 기호 `}|--|{` 와 `}|--o{` 의 상세 비교:
  - `}|--|{` (필수 다대다 관계): 양쪽 엔티티 모두 상대방 데이터가 최소 1개 이상 필수적으로 요구되는 관계 (예: 결제 주문과 주문 상품 간 관계)
  - `}|--o{` (필수 대 선택 다대다 관계): 한쪽은 상대방 데이터가 최소 1개 이상 필수이나, 반대쪽은 상대방 데이터가 0개(없음)일 수 있는 관계 (예: 학생과 수강 과목 간 관계)

## 1.5 화면 설계서 (UI Wireframe)
### 1.5.1 정의
사용자 관점에서의 웹 서비스 화면 구조, 주요 레이아웃 영역, 폼 입력 필드 및 화면 간 이동 흐름을 시각적으로 구성한 화면 뼈대 설계 문서.

### 1.5.2 작성 필요성 및 목적
- 화면 기반 데이터 요구사항 명확화: 스프링 부트 컨트롤러 요청 URL 및 Thymeleaf 뷰에 전달할 모델 데이터 항목 사전 정립
- 기획 오차 감소: 화면 상의 버튼, 검색 폼, 입력 검증 항목을 미리 정의하여 개발 진행 시 화면 재작업 방지

### 1.5.3 필수 포함 항목
- 주요 레이아웃 구획: GNB 상단 바, 헤더 정보, 메인 콘텐츠 영역, 컨트롤 버튼 그룹
- 폼 요소 및 컴포넌트: 입력창, 제출/취소 버튼, 페이지네이션 등 어포던스가 확보된 컴포넌트 배치

### 1.5.4 tldraw 개요 및 산출물 관리 가이드
- tldraw 공식 웹사이트: https://www.tldraw.com/
- tldraw 주요 특징 및 장점:
  - 웹 브라우저 기반 캔버스 도구: 별도의 프로그램 설치 없이 웹상에서 즉시 작동하며 파일 내보내기/가져오기 지원(자체 포맷, SVG, PNG 등)
  - 직관적 와이어프레임 제작: 사각형, 텍스트, 손그림 등 간단한 도구로 복잡한 UI 레이아웃을 손쉽게 표현

- 💻 화면 설계서 샘플: [docs/02_design/03_ui_wireframe.md](docs/02_design/03_ui_wireframe.md)

## 1.6 트러블슈팅 및 기술 문제 해결 기록 (Troubleshooting Log)
### 1.6.1 정의
개발 과정에서 직면한 런타임 오류, 로직 에러, 환경 문제와 그 발생 원인, 해결 방법, 시사점을 기록하는 문서.

### 1.6.2 작성 필요성 및 목적
- 문제 재발 방지: 작성된 해결 기록을 공유하여 팀원들이 동일한 버그로 시간을 낭비하는 현상 차단
- 기술적 자산화: 문제 해결 과정을 통한 수강생 개개인의 기술 역량 성장 및 발표/포트폴리오 자산으로 활용

### 1.6.3 필수 포함 항목 및 작성 템플릿
- 작성자별 식별자 규칙: 동시 편집 충돌 방지를 위한 `TS-[작성자영문]-[순번]` 태그 사용 (예: `TS-YONG-01`, `TS-HARU-01`)
- 복사용 표준 템플릿:

````markdown
## TS-[작성자영문]-[순번]: [발생한 문제 및 에러 제목]

### 1) 발생 현상 및 에러
- 런타임 현상 설명 및 발생한 에러 로그 원문/메시지 수록.

### 2) 원인 분석
- 해당 문제나 버그가 발생한 근본 원인 및 코드 흐름 분석.

### 3) 해결 방법
- 문제를 해결하기 위해 변경하거나 새로 적용한 해결 코드 반영.

```java
// 해결 핵심 소스 코드 반영
```

### 4) 시사점 및 배운 점
- 버그 해결을 통해 새로 배우게 된 원리나 향후 재발 방지를 위한 시사점 작성.
````

- 💻 트러블슈팅 작성 샘플: [docs/03_reports/troubleshooting.md](docs/03_reports/troubleshooting.md)
